## 2. 为什么要这样做

### 2.1 先做 NAS，再做检索，是因为 NAS 是资料源，不是计算中心

企业 RAG 的第一职责不是“先让大模型回答”，而是先把企业资料整理成可以可靠检索的知识源。

NAS 在这个项目里的角色是：

- 存放原始资料
- 做权限隔离
- 提供共享目录
- 作为只读数据源

它不应该承担这些重计算工作：

- OCR
- embedding
- rerank
- 向量库
- 本地大模型
- 大规模解析

原因很简单：

- NAS 的定位是存储与共享
- 检索系统的定位是计算与索引
- 这两类任务的硬件需求不同

### 2.2 先做扫描，再做问答，是因为检索质量依赖数据治理

如果直接上问答，系统很容易出现：

- 找不到文件
- 找到了无权限文件
- 引用了错误页
- 没证据也强行回答

所以我们先做：

1. 文件盘点
2. 文件清单
3. 样本集
4. 评估集
5. 再接入检索和回答

这是企业级 RAG 的正确顺序。

### 2.3 先做只读挂载，是因为原始资料不能被 RAG 过程污染

RAG 的处理链路应该只读访问 NAS，不能反向写回原始资料。

这样做的原因是：

- 原始文档必须保持权威性
- 索引和解析应该是派生数据
- 万一索引出错，不应污染源文件

所以我们一直坚持：

- NAS 只读挂载
- RAG 只生成派生数据
- 原始文件不改、不搬、不覆盖

### 2.4 先用本地电脑/一台服务器，是为了降低前期成本和试错风险

在还没把流程跑通前，不适合直接采购大套设备。

这样做的原因是：

- 先验证项目是否真的有价值
- 先看数据质量和权限问题
- 先看索引和问答是否可靠
- 避免一开始就投入过多硬件成本

我们现在的做法是：

- NAS 继续做数据源
- 本地电脑或 Ubuntu 服务器做检索节点
- 后续再决定是否换 NAS 或买专用服务器

## 3. 当前系统的工作原理

### 3.1 整体原理

当前系统可以理解为一条流水线：

```text
NAS 原始目录
  -> 只读挂载
  -> 文件扫描
  -> 清单生成
  -> 抽样
  -> 解析
  -> 切片
  -> embedding
  -> 向量库
  -> rerank
  -> 带引用回答
  -> 无证据拒答
```

这条流水线的关键点是：

- 上游是文件和权限
- 中间是解析和索引
- 下游是带证据的答案

### 3.2 权限原理

企业 RAG 不能先检索再隐藏无权限内容，而是必须先过滤权限再检索。

正确顺序是：

1. 根据 `knowledge_base` 过滤
2. 根据 `permission_group` 过滤
3. 再做向量检索
4. 再做 rerank
5. 再生成答案

这样做的原因是：

- 避免无权限信息进入候选集
- 避免模型“看见了但不展示”的逻辑漏洞
- 减少数据泄露风险

### 3.3 密钥登录原理

我们现在已经把服务器 SSH 改成了密钥认证。

原理是：

- 私钥留在本机
- 公钥放在服务器 `~/.ssh/authorized_keys`
- 登录时服务器用公钥验证私钥签名

这样比密码登录更适合自动化，因为：

- 可以脚本化
- 可以远程批量执行
- 可以后续无人值守部署

## 4. 下一步计划

### 4.1 下一步目标

下一步的目标不是直接做一个“看起来能聊天”的系统，而是先把企业级 RAG 的基础链路打通：

- NAS 三目录只读挂载
- 真实文件扫描
- 样本文件抽取
- 人工评估集建立
- 检索服务器部署
- 文档解析和索引
- 带来源引用的问答
- 无证据拒答

### 4.2 下一步具体做法

#### 第一步：在服务器上建立项目目录

建议在 Ubuntu 服务器上建立：

```text
~/enterprise-rag/
```

原因是目录要固定，后续所有代码、配置、日志、向量库都放在同一个项目根下，方便维护。

#### 第二步：准备服务目录结构

典型结构可以是：

```text
backend/
configs/
data/
logs/
models/
vectorstore/
```

每个目录的作用：

- `backend`：API 服务代码
- `configs`：知识库、权限、路径配置
- `data`：扫描结果、样本集、评估集
- `logs`：运行日志
- `models`：本地模型缓存
- `vectorstore`：向量库持久化数据

#### 第三步：把 NAS 三目录只读挂载到服务器

挂载到类似：

```text
/mnt/nas/PUR-SHR
/mnt/nas/SALES-SHR
/mnt/nas/product-design
```

原因是统一路径后，扫描脚本和索引脚本都只看这个挂载目录，不需要知道 NAS 的内部细节。

#### 第四步：跑文件清单扫描

扫描脚本会生成：

- `file_inventory.csv`
- `file_inventory.sqlite3`
- `summary.md`

原理是先把所有文件变成结构化清单，再决定哪些文件值得抽样、解析和索引。

#### 第五步：抽样和做评估集

每个知识库先抽样一批代表性文件，再补人工问题。

原理是先验证系统能不能正确引用和拒答，不要求一开始回答所有问题。

#### 第六步：部署检索服务

后面会逐步部署：

- FastAPI
- PostgreSQL
- Qdrant
- 文档解析 worker
- embedding
- rerank

原理是把“数据层”“检索层”“问答层”分开，后期更好维护。

## 5. 你接下来需要知道的几个判断标准

### 5.1 NAS 要不要换

只有当出现以下情况，才值得换 NAS：

- 容量明显增长
- 存储池风险变大
- 需要更多盘位和更强网络
- 需要更强的共享和备份能力

如果只是为了 RAG 计算，不应该优先换 NAS。

### 5.2 云服务器要不要租

云服务器适合：

- 短期验证
- 临时算力
- 远程协作
- 不方便自建机房的场景

但如果要长期处理企业资料，云服务器会面临：

- 长期成本更高
- 数据合规和权限管理更复杂
- 大文件传输成本高

### 5.3 自己买一台服务器是否更合适

如果试点成功、且后续要长期稳定运行，买一台专用服务器通常比长期租云更合适。

原因是：

- 一次性成本可控
- 数据留在内网
- 性能更稳定
- 长期总成本通常更低
